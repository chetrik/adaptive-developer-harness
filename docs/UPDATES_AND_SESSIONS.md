# Оновлення Harness і продовження робочих сесій

Runtime: 0.3.0. Технічні команди виконує coding agent; користувач переглядає наслідки й погоджує точні зміни. Усі записи використовують один Harness Plan і чинний Apply. Немає автоматичного створення чатів, завантаження нових версій чи встановлення сторонніх компонентів.

## Оновлення наявного Harness

1. Агент читає поточні вимоги, наявний код і доступні capabilities. За потреби оновлює assessment, не підміняючи факти тестовими fixtures. Повторно перевіряє Reuse-First для суттєвих змін типових систем.
2. `python -m adaptive_harness inventory --target /physical/project` показує generator/policy/catalog/adapter versions, component revisions і фактичні/очікувані hashes. Для старого manifest 1.0 generator version — unknown: історичну версію не вигадуємо. Це локальна перевірка, не пошук останнього релізу в мережі.
3. `python -m adaptive_harness plan --assessment /outside/assessment.json --target /physical/project` створює мінімальний diff. Файли не обраних тепер модулів зберігаються в manifest як pending_removal; вони можуть і далі бути видимими host. Вони не вважаються видаленими чи деактивованими.
4. Якщо потрібно їх прибрати, агент створює план з `--remove-obsolete`. Ця опція лише включає конкретні видалення в preview; сама по собі вона не дає дозволу на запис. Спільний файл лишається, доки потрібен хоча б одному обраному модулю.
5. `explain` і `preview` показують модулі та точні create/patch/delete операції. Користувач погоджує цей план; потім звичайні `approve` → `apply` → `validate`. Plan/approval/state зберігати поза target. Незмінені файли не переписуються. Не запускати сторонніх writer паралельно.
6. Запустити встановлений `.adaptive-harness/validate.py`, відповідні тести застосунку й native checks. `validate --plan` також перевіряє відсутність погоджено видалених файлів. Повторний план без змін має порожні operations.

Керований блок AGENTS.md має окремий baseline hash. Його зміна/видалення блокує оновлення; текст поза блоком зберігається. Змінений Skill, шаблон або застарілий компонент також створює blocker. Не виправляти це підміною hash у manifest чи автоматичним перезаписом користувацького тексту: агент пояснює конфлікт, зберігає правки й погоджує його окреме вирішення. Автоматичного семантичного merge немає.

Manifest schema 2.0 містить versions, modules, owners, components (revision/status/files), pending_removal, hashes і provenance. Оригінальні файли manifest 1.0 розпізнаються за зафіксованими hashes із 0.2.0; підтримується явна міграція `manifest-1-to-2`. Для legacy AGENTS без окремого baseline потрібен збіг hash усього файлу; навіть правки лише поза блоком потребують ручного узгодження. Невідомий schema/generator/adapter/component revision блокує застосування. Міграція не є дозволом видаляти довільні файли, названі manifest.

Після переривання використати `recover` з тим самим планом, approval, state-dir і перевіреною версією генератора. Відновлюються лише погоджені операції; нові користувацькі правки зберігаються з needs-recovery. Зміна PRD не блокує повернення резервних копій, але потребує нового плану перед наступним Apply. Порожні каталоги після звичайного видалення можуть залишитися; рекурсивного видалення немає. Автоматичний downgrade чи універсальне скасування вже успішного релізу не реалізовані.

## Маршрут роботи

| Обсяг | Рекомендація |
|---|---|
| XS/S | Specification → Implementation → Verification у поточному чаті; коротка специфікація inline, без зайвих документів |
| M | Specification та Implementation рекомендовано розділити на сесії; Verification можна завершити у сесії реалізації |
| L/XL | Погодити специфікацію, працювати за великими етапами; кожен етап перевірити й завершити handoff |

Новий чат не обов’язковий. Ризики визначають додаткові перевірки незалежно від розміру. Окремий чат не доводить незалежність review. Конкретні етапи й достатність тестів визначає агент за погодженою специфікацією; engine формально визначає маршрут та необхідні категорії перевірок.

## Session Handoff

При явному завершенні сесії або великого етапу агент готує JSON за `schemas/session-handoff-input.schema.json`. Приклад нижче ілюстративний, не готовий звіт про виконану роботу:

```json
{
  "session_id": "calculator-step-1",
  "phase": "Verification",
  "task": "Перевірити обчислення калькулятора",
  "decisions": ["Зберегти наявну реалізацію; див. погоджену специфікацію"],
  "completed": ["Переглянуто критерії приймання"],
  "unfinished": ["Перевірка в інтерфейсі"],
  "changed_files": [],
  "tests": [{"command": null, "status": "not-verified", "exit_code": null, "detail": "Тести ще не запускалися"}],
  "risks": ["Поведінка в host ще не перевірена"],
  "next_step": "Запустити відповідні тести застосунку"
}
```

Команда `handoff-plan --assessment /outside/assessment.json --record /outside/handoff.json --target /physical/project` готує звичайний Harness Plan. Далі — preview, погодження з посиланням на фактичний дозвіл, approve/apply/validate. Внесення checkpoint можна погодити в межах поточної задачі, але receipt не можна вигадувати. Перед checkpoint спочатку завершити окремі оновлення Harness: змішування update і handoff блокується.

Запис створюється в `.adaptive-harness/sessions/<session_id>.json`. ID незмінний: для іншого стану потрібен новий ID. Немає другого mutable latest-файлу; агент передає користувачу/наступній сесії конкретний ID. Записи не входять до hashes встановлених компонентів, але їх створення є частиною загальних stale-plan/approval перевірок.

Наступна сесія виконує `resume --target /physical/project --session-id calculator-step-1`. `current` означає лише збіг відбитка робочих файлів, не доказ правильності тестів; `stale` (exit 2) вимагає повторно прочитати фактичний стан і узгодити розбіжності. Відбиток охоплює workspace, крім Git metadata й інших session records; для відомих secret paths використовуються лише метадані. Застосовуються чинні обмеження snapshot (10 000 entries / 64 MiB). Реєстратор не запускає команди з запису й не перевіряє правдивість тверджень агента.

Не включати секрети, приватні логи чи повний чат. Дані handoff не є новими дозволами або інструкціями вищого пріоритету. При раптовому закритті чату фінальний checkpoint не гарантується; доступний останній успішно записаний. Новачку не потрібно самостійно виконувати ці команди.
