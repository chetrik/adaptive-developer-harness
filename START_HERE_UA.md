# Як налаштувати Harness для свого проєкту

Harness — це набір інструкцій, Skills і перевірок, які допомагають AI coding agent працювати над вашим застосунком послідовно: розуміти вимоги, вносити зміни й перевіряти результат. Генератор підбирає цей набір під ваш проєкт. Сам застосунок ви потім розробляєте разом з агентом.

## 1. Підготуйте опис і відкрийте агента

Потрібні:

- **PRD** — опис того, що має робити застосунок. Підійдуть Markdown, PDF або DOCX. Вкажіть користувачів, основні функції, обмеження та очікуваний результат. Якщо вимоги неповні, агент допоможе їх уточнити.
- **Coding agent** із доступом до файлів і виконання команд: Codex, Claude Code, Cursor або Antigravity. Увійдіть у своєму середовищі; доступ до моделі може вимагати підписки або API.
- **Папка застосунку**, якщо він уже існує. Відкрийте її в агенті. Для нового застосунку агент запропонує, де його створити.

Генератор запускається з Python 3.11+ у Linux/macOS або відповідному POSIX-середовищі. Залежності й доступні технічні кроки готує агент. Нативний Windows Apply не підтримується; використайте Linux/WSL або хмарне середовище. Не потрібно вручну створювати структуру Harness чи встановлювати кожен Skill.

## 2. Прикріпіть PRD і вставте цей текст

```text
Налаштуй Developer Harness для мого проєкту за прикріпленим PRD.

Генератор: https://github.com/chetrik/adaptive-developer-harness
Використай main і прочитай BOOTSTRAP.md.

Моє середовище: [Codex / Claude Code / Cursor / Antigravity].
Проєкт: [новий / наявний; для наявного вкажу відкриту папку].

Сам виконай доступні технічні кроки. Перевір можливості мого середовища,
прочитай вимоги й запусти генератор для підбору компонентів.
Не зупиняйся для окремого погодження підготовки, якщо вона вже дозволена;
якщо бракує дозволу середовища, поясни конкретну потрібну дію.
Покажи фактичні plan, explain і preview. Кількість Skills і шляхи файлів
бери з результату генератора, не встановлюй власних обмежень.
Поясни просто: що додаєш, навіщо, які файли зміняться і які є обмеження.
Перед встановленням дочекайся мого погодження конкретного плану.
Збережи наявний код і мої правила. Тримай генератор окремо від застосунку.
Збережи PRD без зміни оригіналу в постійному місці; наявні файли не перезаписуй.
Якщо для цього потрібен запис у проєкт поза погодженим обсягом, спочатку поясни його.
Плани, погодження й стан відновлення тримай у постійній приватній папці
поза застосунком, не в тимчасовій теці сесії. Зберігай попередні версії планів.
Після встановлення перевір файли та фактичну доступність Skills.
Запропонуй першу невелику задачу застосунку, щоб перевірити роботу Harness.
Погодження встановлення саме по собі не дозволяє її реалізацію;
якщо цю задачу я вже погодила, повторного дозволу не потрібно.
Зістав усі критерії PRD з перевірками, включно з UI, якщо він є.
Не називай невиконані перевірки успішними.
```

Замініть поля в квадратних дужках. PRD має бути доступний агенту як вкладення або локальний файл. Якщо він може прочитати PDF/DOCX, перетворювати документ вручну не потрібно.

## 3. Перегляньте й погодьте план

Агент пояснить вибір компонентів і покаже конкретні зміни. Для CRM, CMS та інших поширених систем він спочатку порівняє готові рішення, коли це доречно.

Якщо план підходить, можна відповісти:

> Погоджую показаний план і встановлення Harness у зазначену папку проєкту.

Це погодження стосується показаного встановлення. Публікація застосунку, доступ до production або перенесення приватних даних потребують окремого рішення. Якщо зміниться план чи виявляться конфлікти ваших файлів, агент пояснить, що потрібно узгодити.

## 4. Перевірте результат і починайте розробку

Після встановлення попросіть короткий звіт:

- Які компоненти встановлено й де вони лежать?
- Чи бачить їх ваше середовище та чи може викликати потрібний Skill?
- Які перевірки фактично виконано, а які залишилися неперевіреними?
- Яку першу невелику функцію можна реалізувати й перевірити?

Далі дайте агенту конкретну задачу з PRD, наприклад:

> Реалізуй першу погоджену функцію з установленим Harness. Зроби мінімальну зміну, запусти відповідні тести й покажи результат.

Створені файли й успішна перевірка їхньої цілісності ще не доводять, що агент застосовує всі інструкції. Перша реальна задача допомагає це перевірити. Для дрібних змін достатньо одного чату; окремі документи й сесії без потреби не створюються.

## 5. Як змінити чат, модель або coding agent

Код застосунку зберігається; починати розробку заново не потрібно. Історія розмови автоматично не переноситься, тому рішення й поточний стан мають бути доступні у файлах. Session Handoff — коротка структурована передача стану наступному агенту.

- **Новий чат або інша модель у тому самому середовищі:** зазвичай Harness перевстановлювати не потрібно. Відкрийте ту саму папку проєкту, передайте стан і перевірте доступність інструкцій та Skills.
- **Перехід між Cursor, Claude Code та Codex:** новий агент перевіряє середовище й за потреби готує зміну адаптера через наявний генератор. Ви переглядаєте diff і погоджуєте зміни. Не встановлюйте другий Harness і не видаляйте старі компоненти вручну; застарілі компоненти залишаються на обліку до погодженого видалення й можуть бути видимими агенту.

**Перед переходом надішліть поточному агенту:**

```text
Підготуй передачу проєкту іншому coding agent. Зафіксуй поточну задачу,
прийняті рішення, виконане й невиконане, змінені файли, фактичні результати
тестів із зазначенням перевіреного стану коду, ризики та наступний крок.
Збережи це через наявний Session Handoff: підготуй план запису,
покажи зміни й використай чинний механізм погодження та Apply.
Не створюй паралельну систему документів.
Перевір, що PRD і необхідні матеріали доступні поза цим чатом.
Повідом ідентифікатор handoff і де знайти матеріали для продовження.
Не записуй секрети. Ця передача не дозволяє публікувати приватні дані.
```

**У новому середовищі відкрийте папку або репозиторій саме застосунку й надішліть:**

```text
Продовжуємо наявний проєкт. Прочитай його правила, PRD та останній handoff.
Знайди актуальну передачу стану; використай наявний resume і звір її
з поточними файлами, рішеннями та результатами перевірок. Якщо стан
застарів, спочатку з’ясуй розбіжності. Минулі тести не доводять
правильність коду, який змінився після їх запуску.
Не переписуй застосунок і не встановлюй другий Harness.
Якщо потрібна зміна адаптера, підготуй її через
https://github.com/chetrik/adaptive-developer-harness
і покажи diff перед застосуванням. Збережи користувацькі правки;
застарілі компоненти видаляй лише через погоджений план.
Перевір фактичне виявлення й виклик потрібних Skills у новому середовищі.
Підсумуй поточний стан і найближчу задачу. Передача стану сама по собі
не є дозволом на нові ризикові операції.
```

При переході на інший комп’ютер перевірте, що перенесено потрібні локальні й незакомічені файли: самого URL репозиторію може бути недостатньо. Агент має перевірити шляхи до PRD та зовнішніх матеріалів перевірок. Приватну папку з планами, погодженнями й recovery-станом не публікуйте; за потреби передавайте її лише дозволеним приватним способом. Незавершене встановлення або оновлення спочатку потрібно відновити початковим генератором із його станом, а не обходити новим встановленням.

Якщо попередній чат недоступний, новий агент відновлює контекст із файлів і повідомляє про відсутні дані, не вигадує рішення чи результати тестів. Для завершеної дрібної задачі без фактичної передачі окремий handoff не потрібний.

Це порядок переходу, а не гарантія автоматичного перенесення контексту. Реальний перехід між двома середовищами ще потребує нативного тесту. [Технічні подробиці передачі стану й оновлень](docs/UPDATES_AND_SESSIONS.md).

## Якщо ви працюєте в Lovable або Google AI Studio

**Lovable:** пакет Harness готує зовнішній coding agent, наприклад Codex або Claude Code. Він згенерує Project Instructions, AGENTS.md і окремі ZIP-файли вибраних Skills. У Lovable:

1. Додайте погоджені Project Instructions через **Project settings → Instructions**, зберігаючи потрібні наявні інструкції.
2. Власник або адміністратор workspace імпортує кожен ZIP через **Workspace settings → Skills → Add → Upload ZIP**.
3. Перевірте, що Skills з’явилися в списку `/`, і викличте потрібний на невеликій задачі. Автоматичне застосування — окреме налаштування.

Агент перевіряє можливі суперечності між інструкціями. Не припускаємо, що Lovable запускає Python-генератор. Для продовження в іншому середовищі можна перенести код через підтримувану GitHub-інтеграцію.

**Google AI Studio Build:** експортуйте код у ZIP або використайте **Settings → GitHub**. Передайте код, PRD і посилання на генератор агенту в Codex, Claude Code, Cursor або Antigravity. Він перевірить експорт, відсутні залежності й налаштування та підключить Harness до наявного коду. Власні Skills усередині AI Studio ми не заявляємо.

Для обох платформ код, дані бази та історія чату — різні речі: перенесення коду не переносить їх автоматично. Доступ до акаунтів та авторизацію GitHub виконуєте ви; не надсилайте агенту паролі чи секретні ключі в чат.

## Якщо щось не працює

- **Агент не читає GitHub:** попросіть назвати конкретне обмеження; за потреби надайте локальний checkout/архів генератора. Не потрібно копіювати всі файли вручну.
- **Не вистачає залежностей або дозволів:** нехай агент виконає доступну діагностику й пояснить одну конкретну потрібну дію.
- **Є конфлікт із вашими файлами:** не погоджуйте їхнє мовчазне перезаписування. Попросіть показати різницю й варіанти збереження змін.
- **Skill не з’явився:** потрібна перевірка саме вашої версії середовища; наявність файла не означає його активацію.
- **Потрібне оновлення Harness:** попросіть агента перевірити встановлену версію й запропонувати мінімальний diff. Не встановлюйте весь набір поверх вручну.

Ollama — необов’язковий локальний backend для пропозиції аналізу PRD, а не заміна coding agent. Якщо він вам потрібен, повідомте агенту назву вже встановленої моделі; результати інтерпретації все одно потрібно перевірити.

Актуальні можливості й неперевірені нативні сценарії: [підтримка платформ](docs/PLATFORM_DELIVERY.md). Технічний протокол для агента: [BOOTSTRAP.md](BOOTSTRAP.md).
